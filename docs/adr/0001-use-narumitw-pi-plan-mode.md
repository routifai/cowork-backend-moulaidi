# Use `@narumitw/pi-plan-mode` instead of the hand-rolled `plan-mode.ts`

Status: accepted

`docs/plans/plan-mode-extension.md` built a hand-rolled `src/extensions/plan-mode.ts` after concluding "no standalone pi planner package exists" — it adapted pi SDK's bundled *example* extension instead, deliberately stripping its own bash allowlist (verified conflict with `permission-gate.ts`: both extensions' `tool_call` handlers ran, `curl` was inconsistently flagged) and its progress-marker parsing in favor of the already-installed `todo` tool.

That premise no longer holds: `@narumitw/pi-plan-mode` is a real, published, actively-maintained npm extension (installed via `pi install npm:@narumitw/pi-plan-mode`) offering meaningfully more than the hand-rolled version — a `plan_mode_question` clarification tool, plan persistence/export/save-for-later, and statusline indicators — none of which existed in v1. Decision: adopt it, and retire `plan-mode.ts` entirely.

## Consequences

- **The bash-gating conflict is back, and deliberately accepted this time.** `@narumitw/pi-plan-mode`'s `tool_call` handler (`tool-policy.ts`) independently gates the `bash` tool with its own hardcoded safe-command list, no confirm path for anything outside it. Traced the SDK's actual dispatch (`extensions/runner.js:656-674`, `emitToolCall`): handlers run in **registration order**, and the first one returning `block: true` short-circuits the rest — so whichever of `permission-gate.ts` / `pi-plan-mode` registers first determines the effective policy for any given bash call during planning, not both. Accepted as a known limitation rather than re-solved, per explicit direction to use the real extension over maintaining a custom fork of its safety logic.
- **`plan-mode.ts` and `plan-mode.test.ts` are removed**, not deprecated in place — keeping both active makes `/plan` unreachable (SDK auto-disambiguates same-name commands across extensions to `plan:1`/`plan:2`; the frontend's toggle sends the literal string `"/plan"`).
- **Dev vs. production parity gap, now being closed.** `DefaultResourceLoader` (`agent-init.ts`'s `buildResourceLoader()`) already natively resolves `~/.pi/agent/extensions/*.ts` loose files and `settings.json`'s `packages` array against real `node_modules` — this is why `permission-gate.ts`/`todo.ts` were already active in dev despite `disk-extension-loader.ts` being "dead code" per the root `CLAUDE.md` gotcha. That dead code only matters for the *bundled* production app, which has no real `node_modules` for native resolution to walk. Re-wiring it (this project) makes the shipped app match dev: `pi-plan-mode` plus all 6 loose extensions (`permission-gate`, `todo`, `custom-compaction`, `project-trust`, `reload-runtime`, `summarize`) become active in production for the first time, not just plan mode in isolation — explicitly chosen over a narrower npm-only filter.
