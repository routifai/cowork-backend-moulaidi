# Imported Template reuses the Preset Template schema exactly

Imported Templates (user-uploaded `.pptx` → vision/LLM-extracted design) generate a `template.json` in the same shape Preset Templates use, rather than a reduced v1 schema, so the existing renderer/binding code needs zero changes to consume one.

**Correction (after implementation began):** the original version of this ADR described that shape as `merged_components[] → variants[] → elements[]`. Direct inspection of `template-binding.ts` and `template-schema.ts` showed this was wrong — the actual renderer (`buildTemplateLayoutModel`, `templateSlideUi`) and the content-schema deriver (`getTemplateSchema`, `_templateLayoutSchema`) both read only the top-level `layouts[]` array, where each layout embeds its own `components[]` directly (`{id, description, position, elements}`). A repo-wide grep for `merged_components`/`variants` outside this feature's own new code returned zero matches: those top-level fields exist in the shipped Preset Template JSON files but are not consumed anywhere in this codebase — dead data, likely a leftover from presenton's original authoring pipeline.

The load-bearing shape is therefore just `layouts[]`. Imported Template generation produces `layouts[]` directly (one entry per slide, from the per-slide vision step) with no separate LLM-driven clustering/merging pass — that pass would have existed solely to build `merged_components`, which nothing reads. A `merged_components[]` array is still included in the output for structural parity with Preset Templates (in case something starts consuming it later), but it's derived mechanically from `layouts[]` in plain code (group components by id, treat each occurrence as a variant) — no model call.
