# Smart generation splits into an outline phase and N parallel per-slide calls

Smart presentation generation was one blocking `completeSimple` call that wrote the entire deck's HTML in a single response. Measured against a real model: ~55s for a 4-slide deck, all of it spent waiting on one response with no partial results possible. The straightforward fix — fire one call per slide concurrently instead of one call for the whole deck — was rejected as-is: N calls given the same full source content and told "you're slide K of N" have no way to coordinate what content lands on which slide, so they reliably duplicate coverage or leave gaps. The single-call approach avoided this by construction (one model sees the whole deck and divides the source itself) but paid for it with full serial latency.

Decided instead: split generation into two phases.

1. **Outline phase** (one call, not parallel): produces a per-slide plan — `{title, slide_type, topic/key points}` for every slide — plus a shared design brief (palette, tone, layout conventions) so the parallel phase doesn't lose the visual consistency the single-call approach got for free. The table-of-contents slide, when enabled, is generated here too, since it needs every other slide's title and titles exist at this point even though slide HTML doesn't yet — it is not one of the N uniform parallel calls.
2. **Slide phase** (N calls, concurrent, capped): each call is scoped to exactly one outline entry — its own title/topic/type plus the shared design brief, in an isolated conversation with no index parameter needed (the outline entry is captured by closure) — and writes that slide via an explicit `write_slide(html)` tool call rather than a delimited text blob. Both phases use the same lightweight `ModelRuntime.completeSimple` + `tools` mechanism chat/service.ts's edit loop already uses, not a full `AgentSession` (checked directly: no headless, non-workspace-bound `AgentSession` exists anywhere in this codebase — every one requires a real session file and the interactive extension stack, so retrofitting it for a one-shot background task would be new infrastructure, not reuse). This subsumes what an earlier same-session prototype called `attemptTargetedRepair` (a special-case single-slide fix-up loop, since deleted) — under the two-phase design every slide already goes through its own isolated retry loop from the start, so a separate repair path for "the whole deck failed, fix just this slide" is redundant.

The shared design brief is placed in each slide call's `systemPrompt` specifically so it forms an identical, stable prefix across all N calls — `cacheControlFormat: "anthropic"` (already supported by the vendored `@earendil-works/pi-ai` layer) marks it as an Anthropic prompt-cache breakpoint automatically. This is a genuine trade-off, not a free lunch: total input tokens across the deck go up roughly Nx versus the old single call (each slide call repeats the brief), caching offsets most but not all of that cost, and a cache hit requires (a) a prefix of at least ~1,024 tokens for Sonnet-class models — the brief may need padding/verification to actually clear this, and (b) the parallel calls to not start at the exact same instant, since a cache entry only exists once the first call's response begins streaming. The slide phase therefore fires call 1 first and starts calls 2..N a beat later rather than all via a single simultaneous `Promise.all`.

Concurrency across the N slide calls is capped (not unbounded) to avoid tripping the model provider's own rate limit on large decks — mirrors the `RENDER_CONCURRENCY = 6` precedent already used elsewhere in this codebase for concurrent export rendering, rather than introducing a new pattern.

**Verification status (as implemented):** structural correctness is confirmed against a real model — a 4-slide run produced well-formed, correctly-ordered outline/slide progress events with genuine out-of-order concurrent completion (slide 4 finishing before slide 2). Clean head-to-head timing against the old single-call baseline is not yet established: the two runs used for comparison so far were confounded by the test API key running low on credits partway through this work (one 10-slide run failed outright with "credit balance too low"; the 4-slide comparison that preceded it may have been degraded by the same underlying issue rather than reflecting steady-state performance). A real finding did come out of chasing that failure, independent of the credits issue: the retry loop was burning through its full round budget retrying a non-retryable provider error (billing/auth) instead of failing immediately — fixed (`throwOnProviderError`, checks `stopReason === "error"` right after every completion) and confirmed directly: 1 call instead of 4 against the same real billing failure. A clean timing comparison against the old baseline is still outstanding, pending restored API credits.
